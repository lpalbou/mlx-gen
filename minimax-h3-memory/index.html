    MiniMax-H3 Memory, Speed And Quantization¶

    MiniMax-H3 has 59 billion parameters across its transformer and its conditioner. This page explains how MLX-Gen runs it in a fraction of the memory those weights occupy, what each mechanism costs in time, how the quantized packages compare with the released 16-bit weights, and which tests stand behind every number. For commands, prompting and sizing see MiniMax-H3 video with audio; for the quantization policy of every model family see Quantization.

    Summary¶

    Peak memory of one 960x544, 124-frame, 8-step clip (minimax-h3-turbo-544p), as the whole-process physical footprint on an Apple M5 Max with 128 GB:

    Weights Default --low-ram --stream-blocks --low-ram
    16-bit, as released (AbstractFramework/minimax-h3-bf16) 54.4 GiB 44.0 GiB 11.7 GiB
    8-bit (AbstractFramework/minimax-h3-8bit) 37.0 GiB 26.3 GiB 11.1 GiB
    Mixed 4-bit (AbstractFramework/minimax-h3-4bit) 32.5 GiB 21.9 GiB not measured
    • Same clip in every mode. The three modes write byte-identical MP4 files for the same weights, prompt and seed. The modes change where weights wait between uses, not what is computed.
    • Speed. --stream-blocks adds about 3% to a step on average and --low-ram roughly 5 to 13%; see Speed.
    • Quality. The 8-bit package's video velocity differs from the 16-bit prediction 1.2 to 2.0 times as much as a 0.1% change of the prompt embedding does (audio: 1.3 to 3.0 times), and it keeps the sharpness of the 16-bit clips. The mixed 4-bit package is further away and measurably softer; see Quality By Width.

    Smallest memory each combination completed a clip within, tested on the 128 GB Mac with the rest of its memory locked (see Tested Machine Sizes for how these were run):

    Weights Default --low-ram --stream-blocks --low-ram
    16-bit 96 GB 64 GB 32 GB
    8-bit 48 GB 36 GB 24 GB
    Mixed 4-bit not tested 32 GB not tested

    What A Run Holds In Memory¶

    A clip is made in three stages, and each stage needs different weights:

    flowchart LR
    prompt["Prompt and optional keyframe"] --> conditioner["Conditioner<br/>Qwen3-VL, 50 layers<br/>26 to 48 GiB on disk"]
    conditioner --> embedding["Prompt embedding<br/>a few MB"]
    schedule["Timesteps of the schedule"] --> adaln["AdaLN projections<br/>13 to 24 GiB on disk"]
    adaln --> tables["Modulation tables<br/>about 0.2 GiB"]
    embedding --> denoise
    tables --> denoise
    subgraph denoise["Denoise: every step runs the 50 blocks in order"]
        direction LR
        b1["Block 1"] --> b2["Block 2"] --> b3["..."] --> b50["Block 50"]
    end
    denoise --> vae["Video VAE and audio VAE<br/>5.4 GiB"]
    vae --> clip["MP4 with a stereo soundtrack"]
    Part 8-bit 16-bit When it is needed Where it waits
    Conditioner (50 Qwen3-VL layers, token embeddings, vision tower) 26.0 GiB 48.0 GiB About 3 seconds per prompt, to encode it On disk; read one layer at a time during the encode
    AdaLN projections (one per block, 13B parameters) 12.9 GiB 24.2 GiB Once per schedule, to compute the modulation tables On disk; read block by block for that one pass
    Transformer blocks, token refiner, heads 20.0 GiB 37.5 GiB At every denoise step In memory, or on disk with --stream-blocks
    Turbo adapter 1.3 GiB 1.3 GiB At every denoise step In memory
    Video and audio VAE 5.4 GiB 5.4 GiB For a keyframe, and for the decode On disk until their first use

    On top of the weights a run needs working memory for the packed sequence (about 2 to 4 GiB at 960x544) and the MLX buffer cache (up to 8 GiB by default, 1 GB with --low-ram).

    The Conditioner Is Read For The Length Of An Encode¶

    The conditioner turns the prompt into an embedding once per prompt. Its 50 layers run one after another, so MLX-Gen reads a layer from disk, runs it and releases it before reading the next. The encode peaks at 3.2 GiB for a text prompt and 4.6 GiB with a keyframe, at 16-bit, and takes about 3 seconds when the files are in the system file cache. The embedding of a prompt is kept, so repeating a prompt does not read the conditioner again.

    AdaLN Projections Become Tables¶

    Each transformer block has a projection that turns the timestep into six modulation tables. Its input is the timestep alone, and a run uses a handful of timesteps that are all known before the first step. MLX-Gen therefore computes every block's tables for the whole schedule in one pass over the projections on disk (about 3 seconds), and never holds the projections. The tables are the values the projection would produce during the run. A schedule's tables are kept for the next clip with the same steps, shifts and keyframe use; the two most recently used schedules stay.

    An adapter that trains the per-block AdaLN projections needs them in memory to apply to, so with such an adapter the projections are loaded and the tables are not used. The lightx2v Turbo adapters train attention and feed-forward layers only.

    VAEs Are Read At Their First Use¶

    The video VAE encoder is read when a keyframe is encoded, and the decoders when the first clip is decoded. They stay in memory for the following clips.

    --low-ram¶

    --low-ram lowers the MLX buffer cache from its default (an eighth of the machine's memory, at most 8 GiB) to 1 GB and frees the transformer before the decode. With several seeds in one command the transformer is read again for each seed.

    --stream-blocks¶

    The transformer is a chain of 50 blocks. At every denoise step the packed sequence goes through block 1, then block 2, and so on to block 50, and each block is used once per step. While one block runs, the weights of the other 49 are idle.

    flowchart LR
    subgraph disk["On disk"]
        direction LR
        d1["Block 1"]
        d2["Block 2"]
        d3["Block 3"]
        dn["..."]
        d50["Block 50"]
    end
    subgraph memory["In memory during one step"]
        running["The block that is running<br/>0.4 GiB at 8-bit, 0.7 GiB at 16-bit"]
    end
    d1 -. "read, run, release" .-> running
    d2 -. "then read, run, release" .-> running
    d3 -. "then" .-> running
    d50 -. "last" .-> running

    By default all 50 blocks are in memory for the whole run. With --stream-blocks each block is read from disk just before it runs and released right after, so the transformer costs one block of memory instead of 20 GiB (8-bit) or 37.5 GiB (16-bit). The blocks are read again at every step: 19 GiB per step at 8-bit and 36 GiB at 16-bit. Every block still runs at every step, and the result is the same to the last bit.

    • Streaming works from a prepared package, or from the source snapshot without --quantize. A source snapshot quantized at load time would be quantized again at every step, so there the option is reported as not applicable and the transformer stays in memory.
    • Step time then depends on how fast the disk delivers the blocks. The measurements on this page are from the internal SSD of the test machine.
    • The CLI prints how much is read per step and from where.

    Usage¶

    # Default: the transformer in memory, everything else read when it is needed.
mlxgen generate --model AbstractFramework/minimax-h3-8bit --base-model minimax-h3-turbo-544p \
  --prompt "A red fox trots through fresh powder snow in a birch forest at dawn." \
  --seed 42 --output fox.mp4

# Less memory: a smaller MLX cache, and the transformer freed before the decode.
mlxgen generate --model AbstractFramework/minimax-h3-8bit --base-model minimax-h3-turbo-544p \
  --prompt "..." --seed 42 --low-ram --output fox.mp4

# Least memory: the transformer blocks read from disk at every step.
mlxgen generate --model AbstractFramework/minimax-h3-8bit --base-model minimax-h3-turbo-544p \
  --prompt "..." --seed 42 --stream-blocks --low-ram --output fox.mp4

# The released 16-bit weights, from the 16-bit package or from the source snapshot.
mlxgen generate --model AbstractFramework/minimax-h3-bf16 --base-model minimax-h3-turbo-544p \
  --prompt "..." --seed 42 --output fox.mp4
mlxgen generate --model minimax-h3-turbo-544p --prompt "..." --seed 42 --output fox.mp4

    From Python, stream_blocks is a constructor argument and release_transformer an argument of generate_video; mx.set_cache_limit is the cache part of --low-ram:

    import mlx.core as mx

from mflux.models.common.config import ModelConfig
from mflux.models.minimax_h3.variants import MiniMaxH3

mx.set_cache_limit(1_000_000_000)
model = MiniMaxH3(
    model_config=ModelConfig.from_name("AbstractFramework/minimax-h3-8bit", base_model="minimax-h3-turbo-544p"),
    model_path="AbstractFramework/minimax-h3-8bit",
    stream_blocks=True,
)
video = model.generate_video(seed=42, prompt="A red fox trots through fresh snow at dawn.")
video.save("fox.mp4", export_json_metadata=True)

    Without stream_blocks, pass release_transformer=True to generate_video to free the transformer before the decode. The metadata sidecar records what a run used: modulation_tables, transformer_blocks_streamed and transformer_released.

    Speed¶

    The cost of each mode is measured on one transformer call with identical inputs, alternating the candidates in one process so that the state of the machine affects them equally (seconds per call, mean of three or four calls).

    Blocks in memory against blocks read from disk:

    Canvas 16-bit in memory 16-bit streamed 8-bit in memory 8-bit streamed
    640x352 37.5 s 40.7 s 40.7 s 42.1 s
    960x544 116.6 s 120.6 s 120.1 s 123.1 s

    The default MLX cache (8 GiB on the 128 GB test machine) against the 1 GB cache of --low-ram, 8-bit package:

    Canvas Default cache 1 GB cache
    640x352 41.0 s 45.2 s
    960x544 106.4 s 115.3 s

    The two tables come from different sessions, so compare values within a table, not across them.

    • --stream-blocks adds about 3% to a step on average at 960x544; across paired calls the difference ranges from none to about 14%, with the weight files in the system file cache.
    • --low-ram adds roughly 5 to 13% to a step at 960x544 through its smaller cache. Freeing the transformer before the decode costs one more read of the transformer for the next clip of the same process, a few seconds.
    • The 16-bit and 8-bit transformers take the same time per step at 960x544.
    • With 96 GiB of RAM locked away, which leaves no room for the system to cache the weight files, a 16-bit streamed clip took 1026 s against 1034 s without the lock.
    • A new prompt costs one read of the conditioner (about 3 seconds from the file cache); a new schedule costs one pass over the AdaLN projections (about 3 seconds).

    Whole clips at 960x544, 124 frames and 8 steps took 887 to 1096 seconds from the 8-bit package and 967 to 1260 seconds from the 16-bit weights on the test machine, in its Automatic power mode on mains power. Consecutive runs get slower as the machine warms up: the same 16-bit run took 967 seconds early in a session and 1260 seconds as the fifth run in a row. Whole-clip times therefore do not separate the modes on that machine; the per-call figures above do.

    Tested Machine Sizes¶

    Each row is one 960x544, 124-frame clip generated on the 128 GB test machine while a second process held the stated amount of RAM locked for the whole run. Locked memory cannot be swapped or compressed, so the run sees a machine with that much less memory, including less room for the system file cache. Every clip completed and is byte-identical to the clip of the same weights generated without a lock.

    The 16-bit rows ran from the source snapshot, whose weights the 16-bit package repacks unchanged; the 8-bit rows ran from the 8-bit package as first published, which differs from the current one only in the choice of each weight's level and has the same size; the mixed 4-bit row ran from the source snapshot with --quantize 4, which gives the package's clips. The lock removes memory; a Mac of that size also sets its default MLX cache and its memory checks from its own size, which the emulation does not reproduce.

    Weights Mode RAM locked Mac size emulated Peak footprint Time
    16-bit default 32 GiB 96 GB 54.9 GiB 1008 s
    16-bit --low-ram 64 GiB 64 GB 44.0 GiB 1036 s
    16-bit --stream-blocks --low-ram 96 GiB 32 GB 11.6 GiB 1026 s
    8-bit default 80 GiB 48 GB 37.3 GiB 1010 s
    8-bit --low-ram 92 GiB 36 GB 26.3 GiB 1613 s
    8-bit --stream-blocks --low-ram 104 GiB 24 GB 10.9 GiB 1010 s
    Mixed 4-bit --low-ram 96 GiB 32 GB 21.6 GiB 1262 s

    The 8-bit --low-ram run at 36 GB took about 55% longer than the same run without a lock: at that size the transformer and the rest of the system compete for memory. At 36 GB and below, --stream-blocks --low-ram is the faster choice. Other applications' memory counts on a real machine; close memory-heavy ones before a run near the low end of a range.

    At 1344x768, 124 frames, the default mode peaks at 38.3 GiB with the 8-bit package and 55.7 GiB with the 16-bit weights.

    Quality By Width¶

    Quantization changes the weights, so it can change the picture. Two measurements compare each width with the released 16-bit weights.

    Velocity error. The 16-bit model generates three reference clips (a dialogue shot, a fox in snow, and the fox from a keyframe; 640x352, 124 frames, 8 steps, seed 42), and its transformer inputs are recorded at steps 1, 4 and 7. Each candidate then predicts the velocity on those same inputs, with its own conditioner's embedding of the prompt, and the result is compared with the 16-bit prediction as a relative RMS error. The noise floor is the error of the 16-bit model itself when its prompt embedding is changed by 0.1%: it shows how much the prediction moves for a change far smaller than any quantization.

    Video error / audio error at each recorded step:

    Clip and step Noise floor 8-bit package Mixed 4-bit package
    Dialogue, step 1 5.9% / 1.1% 8.9% / 2.4% 15.9% / 6.2%
    Dialogue, step 4 6.8% / 2.0% 9.0% / 2.8% 16.0% / 6.5%
    Dialogue, step 7 3.0% / 1.1% 3.8% / 1.9% 7.4% / 4.8%
    Fox, step 1 4.2% / 1.4% 6.0% / 1.9% 12.4% / 6.5%
    Fox, step 4 4.3% / 2.4% 6.2% / 7.2% 13.3% / 10.7%
    Fox, step 7 2.9% / 1.0% 3.5% / 2.0% 7.1% / 3.6%
    Fox, image-to-video, step 1 5.7% / 1.5% 11.3% / 2.0% 30.4% / 5.6%
    Fox, image-to-video, step 4 3.3% / 1.7% 4.8% / 3.6% 11.2% / 10.0%
    Fox, image-to-video, step 7 2.0% / 1.1% 2.6% / 1.5% 5.0% / 4.0%

    Same-seed clips. Median frame PSNR of each candidate's clip against the 16-bit clip, and the fine detail of the frames (variance of the Laplacian, as a percentage of the 16-bit clip's):

    Clip 8-bit package Mixed 4-bit package
    Dialogue 22.8 dB, 98% 18.1 dB, 88%
    Fox 28.2 dB, 101% 24.2 dB, 80%
    Fox, image-to-video 21.0 dB, 98% 16.0 dB, 109%
    • The noise floor is 2 to 7% of video velocity: the model amplifies any small change, so two runs that differ slightly drift apart over the steps. Same-seed PSNR therefore measures how far two clips diverge, not which one is better.
    • The 8-bit package's video velocity differs from the 16-bit prediction 1.2 to 2.0 times as much as a 0.1% change of the prompt embedding does (audio: 1.3 to 3.0 times), and the package keeps the fine detail of the 16-bit clips (98 to 101%).
    • The mixed 4-bit package's video velocity differs 2.4 to 5.3 times as much (audio: 3.3 to 6.0 times); it diverges further at clip level, and loses 12 to 20% of the fine detail on the two text-to-video clips.
    • The measurements cover three clips at one seed and one canvas.

    How The 8-bit Weights Are Chosen¶

    MLX stores a quantized layer as groups of 64 weights, each group with its own grid of 256 levels (a start value and a step). MLX picks every weight's level on a float32 grid and stores the grid at the layer's own 16-bit precision. With 256 levels that rounding of the grid is as large as one step, so about one weight in five is then one level away from its nearest. MLX-Gen picks the levels again on the grid that is stored. The size, the memory and the speed are unchanged, and the weight error of a layer falls by about a quarter (0.78% to 0.59% on a sampled attention layer). At 6 bits and below a step is too wide for the rounding to matter, so those widths are quantized as MLX does it. On whole clips the effect is within the variation between runs: the package's mean video velocity error is 6.2% with this choice against 6.3% with MLX's, three of nine recorded inputs score slightly worse, and the same-seed clips sit 0.2 to 2.7 dB further from the 16-bit clips.

    How The Results Were Validated¶

    Claim Test
    The staged loading does not change the output Clips from the 8-bit weights at 640x352, 960x544 and 1344x768 and from the mixed 4-bit weights at 640x352 and 960x544, text-to-video and image-to-video, are byte-identical MP4 files to the clips the whole-model loading path wrote from the same weights
    A streamed conditioner equals one held in memory The prompt embeddings of three prompts, one with a keyframe, are bit-identical
    AdaLN tables equal the projections The 16-bit transformer with tables predicts exactly the velocity of the 16-bit transformer with its projections in memory (relative error 0.0 on nine recorded inputs)
    Streamed blocks equal blocks in memory Bit-identical transformer output at 640x352 and 960x544, at 16-bit and 8-bit, and byte-identical clips
    --low-ram and --stream-blocks do not change the clip Byte-identical MP4 files against the default mode, for 8-bit and 16-bit
    A package gives the clip of load-time quantization The clip from AbstractFramework/minimax-h3-8bit is byte-identical to the clip from the source snapshot with --quantize 8
    The memory figures The peak physical footprint the operating system reports for the whole mlxgen generate process, from each run's metadata sidecar
    The machine sizes Runs with RAM locked by a second process, listed in Tested Machine Sizes

    The unit tests in tests/minimax_h3/test_h3_staged_loading.py and tests/common/test_streaming_weight_loader.py repeat the equalities on small models: streamed against in-memory conditioner, tables against projections at 16, 8 and 6 bits, streamed against in-memory blocks with and without an adapter, a whole clip with and without tables, the refusal of a weight file that changed after the model was loaded, and the 8-bit level choice.

    tools/minimax_h3_memory_probe.py produces the reference clips, the recorded inputs, the velocity errors and the alternating timings; tools/minimax_h3_quant_probe.py ballast --gib N locks RAM for the machine-size runs. docs/assets/quantization/minimax-h3/reference_report.json holds every velocity error, per-call timing and mlxgen generate run behind this page.

    Limits¶

    • A weight file must not be replaced while a model that reads from it is loaded. Weights that have not been read yet would come from the new file, so MLX-Gen checks the files before it reads streamed transformer blocks, the AdaLN projections and the VAEs, and stops with an error when one changed. The conditioner is read in full at each encode, so it is not part of that check.
    • --stream-blocks reads 19 to 36 GiB from disk at every step. It was measured on an internal SSD; a slower disk lengthens every step by the time of those reads.
    • An adapter that trains the per-block AdaLN projections keeps them in memory (12.9 GiB at 8-bit, 24.2 GiB at 16-bit) and disables --stream-blocks.
    • mlxgen prepare writes a package one component at a time and holds one component in memory at a time; the largest is the transformer, 33 GiB at 8-bit and 62 GiB at 16-bit.
    • The machine sizes were emulated on one 128 GB machine; they were not run on Macs of those sizes.
    • Byte-identical clips are a property of one environment. Another MLX version changes the arithmetic slightly, and the same seed then gives a clip that differs as much as the 8-bit and 16-bit clips differ from each other (28.9 dB median frame PSNR between MLX 0.31.0 and a later release, same package and seed).
